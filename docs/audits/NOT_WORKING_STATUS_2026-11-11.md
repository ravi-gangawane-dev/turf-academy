**Residual P1 defects carried into P2:**
- **P-09 Stored PDF staleness** — resolved on 11 November 2026. Legacy stored receipt files are no longer surfaced in the parent portal; receipts are rendered from live records (formerly P2-6, now removed from the table).
- **P-11 CSV safety residual** — resolved on 11 November 2026. Coach-portal and attendance-calendar exports now use the shared CSV builder (UTF-8 BOM and formula-injection escaping); both use the shared export dialog.

**Resolved in this pass (11 November 2026):**
- **P1 invitation fallback link** — the invite dialog now offers **Create a link instead**, and pending/failed/expired rows offer **Copy link**. The new Edge `link` action validates the role against the catalogue, refuses confirmed accounts (`account_exists`, so an admin cannot take over an existing login), reuses or updates the invitation row, and calls `auth.admin.generateLink` (`invite` for new accounts, `magiclink` for unconfirmed existing accounts). The returned link is shown once to the signed-in admin in a custom dialog, is never emailed or written to the audit log, and the audit entry is `invitation_link_generated`. This removes the SMTP dependency for account activation but does not replace the provider-delivery proof, so the P1 items stay Partial until a real mailbox accepts an invitation.
- **P2-6 Stored receipt freshness (P-09 residual)** — the parent portal no longer offers legacy stored receipt files as the receipt of record. The receipt screen and its preview/print/PDF actions always render from the live payment record, and the per-row `createSignedUrl` calls were removed, so one storage request per payment row is gone as well. `ParentPortalService` test coverage asserts the receipt is returned without a signed URL.
- **P2-7 Legacy receipt signed-URL download (P-08 residual)** — the “View stored copy” action was removed, so the portal never opens a short-lived URL. PDF export continues through the preferred browser print dialog, now with a stable suggested filename derived from the document (`Receipt-RCP-42`, `Batch-roster-RST-BMOR`, …) via `printFileName()`, and the original page title is restored when the dialog closes. Covered by `print-document.service.spec.ts`.
- **P2-8 Attendance calendar CSV** — monthly and weekly summaries now render as tables behind the shared `TableTools` export dialog; the record list uses a server-side loader that exports every matching page. Column definitions and row builders move to `attendance-calendar-export.ts`; the old bespoke CSV string builder was removed.
- **P2-9 Coach portal attendance CSV** — the duplicate custom export button was removed. The attendance table now uses `TableTools` with real column keys and `CoachPortalService.attendanceHistoryAll()`, which pages through every filtered record instead of only the visible client list.
- **Code quality gate** — `npm run lint` now passes with zero errors. Fixed explicit `any` in batch workspace, domain services, batch details and fees; removed unused declarations; added `role="presentation"` to the export, ID-card and print-preview backdrops so the accessibility rules see them as non-interactive.

**Resolved on 12 November 2026:**
- **P2-1 Student/parent/coach profile sheets** — added a shared `profile-sheet` print document with A4 portrait styling (`@page profile-page`). Student, parent and coach details pages now offer **Profile sheet** beside the existing ID-card action and open the sheet in the shared preview destination. Every value comes from the live record: student sheets include personal/contact/guardian/enrollment/attendance sections, an optional medical section (only when the record is returned), a completeness checklist and the actual `student_documents` rows grouped by document type; parent sheets include contact, address, account and linked-student sections with a profile checklist; coach sheets include contact, employment, specialisation, assigned-batch and biography sections with a profile checklist. References are derived from the real academy id (`PRF-STU-…`, `PRF-PAR-…`, `PRF-COA-…`). The checklist states what the academy has recorded; it is labelled in the sheet as a record-completeness view rather than a compliance requirement. The app still has no document-upload screen, so student sheets list documents that already exist in `student_documents` (up to 200 rows, with a note when the total is higher). Verified with 53 focused tests across 7 files, ESLint clean, and a development build.
- **P2-2 Paper size and orientation selector** — the shared print preview now offers **Paper size** (A4, A5, Letter) and **Orientation** (portrait, landscape) controls. The choice is remembered per document type in local storage (`academy-print-page-setup`) and applied to subsequent direct prints as well, through a one-run `@page` override that is removed when the browser print dialog closes. The override also sets the matching content height so explicit page footers still reach the paper edge, reproduces the existing per-document margins, and leaves the preview paper width in step with the chosen sheet; **Use default** clears the remembered choice. CR80 ID cards stay fixed on A4 portrait because the card and crop geometry is physical, and the preview says so instead of showing an unusable selector. Verified with 42 focused tests across 4 files (helpers, preference service, preview, print service), ESLint clean, and a development build.

**Resolved on 14 November 2026:**
- **P2-3 Configurable letterhead/footer** — Settings has a new **Print & Documents** section (`/settings/print`) with three optional fields: **Registration number** (60 characters), **Terms and conditions** (1,200 characters, used in invoice and statement notes) and **Footer note** (200 characters, printed on every document footer). Empty values keep the existing template wording, so no academy is forced to change its stationery. The values flow through the shared print brand into every print template (matrix, register, roster, enrollment confirmation, statement, table, invoice, receipt, refund and profile sheet). Saves write the base settings first and the print columns in a separate update, so an unmigrated database still saves everything else and only raises a clear “apply the print settings migration” error when print values were entered. Added `supabase/migrations/202611120001_print_document_settings.sql` (nullable columns plus length checks, validated against PGlite). Verified with 125 focused print tests, 9 settings-page tests, 3 settings-service tests, ESLint clean, and a development build. The migration is **not applied remotely** yet, so the three fields will not persist on the hosted database until it is.
- **P2-4 Print queue / batch print** — the shared print pipeline now accepts several live documents in one job instead of a single document. Student List rows have a selection checkbox, a header select-all for the current page and a **Print ID cards (n)** action; the fee Payments list has the same controls with a **Print receipts (n)** action. Selection resets whenever the list reloads (filter, page, sort or search), so a batch always matches what is on screen and is never built from stale rows. Each card keeps its existing duplex CR80 sheet and each receipt keeps its page, with a page break between documents; the preview stacks every sheet and the browser print dialog receives one job. Suggested file names are `ID-cards-batch-N` and `Receipts-batch-N`; a single-document print keeps its existing reference-based name. Every value comes from the selected live rows, and the audit trail records one entry per document. Verified with the full shared print suite (125 tests), a focused Student List selection test, ESLint clean, and a development build. Payments-page tests remain limited by the pre-existing `payments-page.spec.ts` `queryParamMap` mock failure, which is untouched.

**Resolved on 16 November 2026:**
- **P2-5 Localisation (formatting)** — date, time and money formatting now follow the saved academy settings instead of scattered hardcoded locales. `src/app/core/localisation/academy-locale.ts` derives one English locale from `academy_settings.currency_code` (`INR → en-IN`, `USD → en-US`, `GBP → en-GB`, … with `en-IN` fallback) and provides safe date-only helpers. `AcademyPreferencesService` now exposes `timezone` and `locale` signals and uses them in `today()` and `money()`. A new `academyDate` pipe replaces Angular's `date` pipe in app templates, applies the saved timezone, keeps `YYYY-MM-DD` values pinned to UTC so they never shift a day, and re-renders when the academy timezone changes; `academyMoney` uses the derived locale. Print output derives its locale from the document currency too (`printMoney`, `printDateOnly`), and the batch roster, attendance register, enrollment confirmation and profile sheet use the shared helper. TypeScript formatting in exports, dashboards, coach/parent/attendance screens, the offline queue and the mock store/repositories now uses the same preferences; the attendance WhatsApp payload carries the academy name, timezone and locale and passes ISO timestamps so the message is rendered in academy time. Verified with 38 focused test files / 233 tests, ESLint clean, and a development build. **Remaining:** labels are still English-only; translating them needs a target language decision, so this item stays Partial.
- **P2-14 Delete/deactivation policy** — the account lifecycle policy is now documented in `docs/ACCOUNT_LIFECYCLE_POLICY_2026-11-16.md`, grounded in the current schema and Edge behaviour. It defines **Active**, **Disabled (inactive)**, **Suspended** and **Pending activation**; makes disable/suspend the supported removal path; records why many profile references block a hard delete; sets retention rules for financial, attendance, people, audit, invitation and notification records without inventing a legal retention period; defines an operator anonymisation procedure for approved erasure requests; covers re-activation, audit and last-admin/self-removal rules; and states that the DB guard migrations are still local only. The Users screen now says that **deactivation keeps history** and that only an account with no linked records can be permanently deleted. The access confirmation dialog shows human-readable role/status labels, explains the sign-in and retention effect of the selected status before the reason is entered, and labels `inactive` as **Disabled (inactive)**. Focused Users-panel tests cover the role/status wording, the disabled-state retention message, cancellation, reason validation, server errors and access history; ESLint and a development build are run. No remote migration, Edge deployment or hosted RLS/session check was performed.
- **P2-11 Delete user (guarded hard delete)** — the Users screen now offers **Delete** for another account, backed by a guarded `delete` action in the `admin-manage-users` Edge Function. The custom confirmation dialog requires a 3–500-character reason and a checked irreversible-action acknowledgement. The Function refuses a self-delete (`self_delete`), refuses to remove the final active administrator (`last_admin`), and probes every non-cascading `profiles` reference before deleting. If any history exists it returns `account_has_history` with the blocking categories and deletes nothing; the FK constraints remain the final authority if that list drifts. On success it calls `auth.admin.deleteUser` and audits `user_deleted` with the reason and the identity recorded at deletion time, so Access history can still name the row. When a delete is refused for history, the dialog offers **Disable instead**, which opens the normal access-change confirmation pre-set to `inactive` and keeps the reason. `supabase/migrations/202611160001_profile_delete_guard.sql` adds a `BEFORE DELETE` trigger that refuses deleting the caller's own active administrator profile and the final active administrator, including service-role/cascaded deletes. Verified with 35 Edge tests, 8 PGlite DB checks (`npm run test:user-access:db`) and 36 focused Angular tests; ESLint and a development build are run. The Edge change and migration are **local only**; the deployed function remains version 13.
- **P2-10 Create user with temporary password** — the Users screen now has **Create user** beside **Invite user**. The `admin-manage-users` Edge Function accepts `action: 'create'`, validates the same name/email/phone/role payload as an invitation, refuses an email that already has a profile (`account_exists`), and generates a 16-character temporary password server-side with `crypto.getRandomValues` (at least one uppercase, lowercase, digit and symbol, then shuffled). It creates a **confirmed** account with `user_metadata.must_change_password = true`, sets the requested role and an active profile with onboarding cleared, and audits `user_created` without the password. If the profile cannot be prepared the new login is rolled back (`create_profile_failed`) so a half-created account cannot sign in with the wrong role. The password is returned **once** in the response and shown in a custom credential dialog with a copy action; it is never emailed, stored by the app or written to Access history. At the next sign-in `AuthService.mustChangePassword()` reads the metadata, the login page sends the person to `/auth/reset-password`, and `authGuard` keeps every academy route closed until the password is replaced; `changePassword` clears the flag and the normal onboarding/recovery flow resumes. Verified with 41 Edge tests, 66 focused Angular tests across 4 files, ESLint clean, and a development build. The Edge action is **local only** until the function is redeployed; the deployed function remains version 13.
- **P2-13 Per-user permission overrides** — the Users screen now has a **Permissions** action per account, backed by `supabase/migrations/202611160002_profile_permissions.sql` and new `permissions` / `set_permissions` actions in the `admin-manage-users` Edge Function. The migration adds `public.profile_permissions` (one row per account and permission, `effect` = `grant` or `revoke`, required 3–500-character reason, actor and timestamp), RLS that lets an account read its own rows and an administrator read all rows, service-role-only writes, and `public.replace_profile_permissions(...)`, which validates every key/effect/reason before deleting and re-inserting the set atomically. The custom dialog groups the database permission catalogue by area, shows whether each permission is **Included with role** or not, and offers **Role default / Grant / Revoke** per permission plus a reason. `AuthService` loads the signed-in account's rows during session restore and five-minute revalidation and merges them into `hasPermission()`, so menus, routes and action buttons follow an override; a failed or missing table keeps the role matrix as the safe baseline. The Edge Function rejects unknown keys, invalid effects, duplicate keys, a missing reason, a self settings revoke (`self_lockout`) and a settings revoke that would leave no active administrator with settings access (`last_admin`), then writes `user_permissions_changed` with before/after values. **Scope:** the database RLS policies still enforce the base role. A grant cannot widen database row access, and a revoke hides the screen/action but is not a hard API boundary until the policies themselves become permission-aware; this is stated in the dialog. Verified with 56 Edge tests, 12 PGlite DB checks (`npm run test:user-access:db`), 67 focused Angular tests across 3 files, ESLint clean, and a development build. The migration and Edge actions are **local only**; the deployed function remains version 13.
